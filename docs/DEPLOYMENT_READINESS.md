# Deployment readiness checks

Run `npm run check:deployment -- --project-ref YOUR_EXPECTED_REF` to check the configured project without writing data. The optional `--env-file PATH` replaces the default `.env` and `.env.local` files; otherwise `.env.local` overrides `.env`. Shell variables override file values. `--json` is accepted; output is always sanitized JSON. `--help` shows usage. The report identifies the target project by reference, but never prints keys, email addresses, response bodies, or network errors. Review the target before using it. The expected-ref guard stops probes when it does not match.

The check validates the Supabase URL and the shape of a publishable key or legacy anonymous JWT. For a legacy key, its project claim must match the URL. It makes read-only GET requests: public profile columns and the private email column are selected with a zero-row limit; each checked Edge Function is requested with GET. Public fields must succeed and email must be explicitly denied. The email probe accepts 403 or a 401 with Postgres permission-denied code `42501`; other 401 responses remain unknown. A function's 405 confirms the handler rejected the method; a 401 may come from the gateway and is **unknown**, not evidence that the function is deployed or healthy. Missing endpoints, an exposed email field, and unknown results keep readiness false and result in a nonzero exit. Network failures and unexpected status codes are unknown. These checks use anonymous access and do not establish authenticated permissions or application behavior.

The report checks the upload function by default. It also checks the three payment functions only when `VITE_ENABLE_PAYMENTS` is exactly `true`, using the same shell-over-file precedence as the other settings. Pass `--origin http://localhost:5174` (or another exact canonical HTTP(S) browser origin) to send an OPTIONS preflight to the upload function instead of GET. A 204 with the exact allowed origin and POST in the allowed methods confirms the preflight reached a configured handler; a 401 remains unknown and a 503 is unavailable. This preflight does not establish that an authenticated upload or any other functional journey succeeds.

This report does not apply or validate migration history, deploy functions, verify provider settings or server-side secrets, exercise payment flows, or authorize production changes. Separately compare the target's migration history against the reviewed repository migrations, verify the intended function versions are deployed, and check provider configuration and secrets through their management interfaces. Resolve differences deliberately; do not rerun all SQL migrations blindly. Complete authenticated and end-to-end verification in an appropriate environment before release.

The profile privacy repair migration is designed to be repeatable on the narrow legacy profile schema and after the existing hardening migrations. Before applying it, verify the target and migration history and review the resulting grants and policies. After applying, repeat the read-only privacy check and test authenticated profile saves and owner isolation. If an application issue requires rollback, fix forward while keeping private email SELECT denied; do not restore broad profile SELECT grants. This repair does not deploy Edge Functions or configure provider secrets.

The secure image upload function bundles the public origins in `supabase/functions/secure-image-upload/allowed-origins.json` when deployed. Its current fallback permits only `http://localhost:5174`. Update that file with the exact intended browser origins before deploying for another environment. If `ALLOWED_ORIGINS` is present, its comma-separated list replaces the bundled list; an empty or invalid list disables uploads with a 503 response. Use canonical HTTP(S) origins without paths, trailing slashes, wildcards, credentials, or whitespace. Origin configuration is public, not a secret; service credentials remain server-side. Deploying the function and testing authenticated uploads are separate release steps.
